# Design System Loop: approved website positioning

Updated 12 October 2026. Product baseline: 0.4.0. This direction incorporates the user's approved refinement and supersedes the earlier report-first recommendation.

## Promise

**Build and improve your design system with your coding agent.**

Understand what needs to change. Preserve what works. Carry an agreed improvement through code, checks, and a handoff your team can use.

The best-fit audience is a product team using a coding agent without enough dedicated design-system capacity. This is a positioning hypothesis, not a claim supported by customer research. Existing system teams are a secondary audience.

The differentiator is the guided behavior: investigate using measured evidence, preserve legitimate product decisions, carry out agreed work, verify the affected result, and leave a usable handoff. An engine and a companion skill provide the packaging. A report is one supporting artifact, not the promised end result.

## Five-section homepage

1. **Promise.** Concrete headline, audience, a repository starting action, and a link to the completed example.
2. **Worked example.** One bounded, implemented change connects problem → decision → changed component in an example workflow → verification → handoff. The matching “big picture” graphic explains why this work was chosen and is followed immediately by the working before/after previews.
3. **Three starting situations.** Establish a shared foundation; investigate bypasses and drift; review a system change. Each has a prompt, deliverable, and finish line.
4. **How it works.** Investigate and recommend; build and adopt; verify and hand over. One compact retained-decision example explains the loop into the next change.
5. **Start/help.** First reading, agent connection, clear responsibilities, and compact practical answers. Omit commercial help until a verified contact destination and real offer exist.

Detailed maintenance, the dashboard, and the original SaaS illustrations live on the existing non-generated system-example page. Full assessment reports remain linked as supporting evidence. Generated `site/guide/` content remains package-owned.

## Main proof and provenance

The implemented public synthetic settings fixture is in `site/samples/theme-delivery/`; its full delivery page is `site/worked-example.html`.

The token change reuses the existing public `site/demo/before.css` and `after.css`: replace two literal action-background declarations with theme-local palette aliases. The new workflow harness places the shared button in a working, page-local settings form. Both versions have the same form behavior and component CSS. The evidence records actual source checks, 0.4.0 token-only audits, browser color and dimension measurements, keyboard form operation, and a retained decision with reproduction steps.

This demonstrates one completed, bounded improvement. It does not prove a full system setup, customer outcome, production deployment, or business improvement. Local preview saves are not backend persistence. The older `demo/decision.md` remains historical; the new handoff describes the newly measured behavior and any differences.

The original component-workspace consulting report is still a proposal. Its “big picture” supplied the four-stage presentation, but its proposed work is not presented as the implementation of this theme fixture. The homepage's new overview is a matching assessment of the theme delivery. The SaaS animation remains explicitly illustrative. These artifacts must not be spliced into a fictitious engagement.

## Claims and ownership

- Product/source claims: verify against the 0.4.0 engine and skill.
- Main delivery claims: link to the fixture source, browser observations, audit outputs, and handoff.
- Team decisions and agent judgment: distinguish from what the engine can measure.
- Maintenance: saved runs and retained decisions require intentional use. Installation does not activate an agent or schedule work. The optional edit hook is Claude Code-specific.
- Measurement limits: static evidence is not runtime adoption, design quality, or a business outcome. A token-only audit does not establish full accessibility or full-system correctness.
- Public examples: use synthetic/public fixture material and identify its scope. No client material is needed.

## Acceptance through comprehension

Ask target readers, without prompting them with the answers:

1. What does Design System Loop help you do?
2. Who is it for?
3. What work was actually completed in the example, and what was preserved?
4. Which evidence came from code checks, and which from a rendered review?
5. What does the next contributor receive?
6. How does a retained decision help with the next change?
7. What would you do next in your own repository?
8. What would you otherwise use to do this work?

The page must provide a clear answer to the first seven; the eighth tests the positioning against actual alternatives. No reader interview, comprehension study, or customer outcome study has been completed. Do not substitute a subjective score for those checks.

## Implementation acceptance

- Five main homepage sections, preserving the established visual identity and responsive behavior.
- A complete example with discoverable source, measured results, explicit limits, and usable handoff.
- Working desktop/mobile previews, keyboard controls, sample links, and command copying.
- Motion accommodates reduced-motion preferences and content remains usable without reveal animation.
- Build, local-link validation, existing tests, and the dedicated fixture verification command pass.
- No hand edits to generated package docs. No deployment or package publication is part of this pass.

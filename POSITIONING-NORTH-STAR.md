# DS Loop positioning

Updated 2026-10-15 from the owner's clarification and the product's VISION.md.
Use this direction for homepage edits alongside the approved visual design.

## Promise

Approved homepage headline: **Your design-system team, in one install.**
Audience line: **For fast-building teams with growing codebases**
Describe the lifecycle as Investigate → Consult → Build → Keep healthy.
Lead with the full design-system workflow: investigation, an approved plan,
implementation, and ongoing maintenance. The report supports one phase; it is
not the main product promise or hero CTA. Explain how saved decisions feed the next change.


Build and maintain an LLM-ready design system for a fast-moving product team.
Help the organization do the work of a design-system team: assess, recommend,
build, migrate, document, and maintain. Support teams without specialists and
give existing design-system teams more capacity.

LLM-ready means usable shared code, working examples, clear usage guidance,
and recorded decisions that people and coding agents can consult and apply.
Explain these concrete resources whenever using the phrase.

## The loop

Read the code and existing decisions → investigate → agree on a plan →
implement → check the result → update guidance and decision records →
use that context in the next task.

The work changes both the product code and the project knowledge available
for future work. Notes are useful when they inform subsequent decisions.
This is the owner's systems-thinking framing, inspired by Donella Meadows.
Her discussion of information and feedback is background, not product validation:
https://donellameadows.org/dancing-with-systems/

## Message hierarchy

1. Team capacity and a maintainable, LLM-ready design system.
2. Establishment, adoption, and maintenance across a growing codebase.
3. A consulting assessment and plan, followed by agreed implementation.
4. Evidence, checks, and saved decisions supporting that work.

Code auditing and component-usage analysis are supporting capabilities. Do not
reduce the product to those capabilities or lead with a DESIGN.md comparison.
Existing design instructions can remain an input; address that question in FAQ.

## Claim boundaries

Keep the distinction between agent-led work and deterministic engine checks.
Saved project files supply context; do not imply autonomous learning or guaranteed
recall. Hooks and CI need setup. Verification has documented coverage limits.
The theme fix is a verified demo; the component-adoption animation is an
illustration. Neither establishes performance at enterprise scale or replaces
human review. Preserve these distinctions while communicating the full purpose.
